# 可编辑棋盘（形状 + 虚空格）· 增量 PRD

> 本文只描述**一个增量**：让**房主**把棋盘从「固定矩形」改为「**任意方格拼成的形状**」，并可在形状内部划分**虚空格**（= 棋盘外 / 墙，不可落子、阻断连通、不参与计分）。
> 判定语义、房间配置范式、序列化范式**全部复用现状**（尤其复用刚交付的「房主可配置胜利条件」的配置链路），不新造游戏概念。
> 本文不改动任何游戏代码，仅作为架构 / 开发 / QA 的输入。

## 1. 产品定义

### 1.1 产品目标（3 个正交目标）

1. **把棋盘形状交回房主**：现在 go 恒 32×32、rts 恒 192×192 矩形（F1/F2）。改为房主可圈定**任意方格拼成的形状**（1×1…100×100），让同一份玩法支持「十字对局」「双岛割据」「回字围城」等形态，而无需改一行代码。
2. **用虚空格引入「墙 / 边界」这一新地形语义**：虚空 = 棋盘外（R4），棋子贴着虚空即被阻断连通、虚空后方空区不连通。这让「围地」在不对称棋盘上成立，是形状化玩法的核心机制来源；**虚空不参与计分**，不引入「可被包围的洞」这一复杂概念。
3. **两者皆可配、两模式皆生效、入口双轨**：预设模板（4~8 个，可微调）+ 手绘编辑器（R5）；go 与 rts 都生效（R6）。**不配置时行为零变化**（默认 = 现有矩形），不回归。

### 1.2 成功标准（可量化）

| # | 标准 | 目标值 |
| --- | --- | --- |
| M1 | 不配置形状时，**行为与现状逐字节一致** | `npm test` 320/320 全绿；go 32×32 / rts 192×192 默认路径不改变判定结果 |
| M2 | 形状配置可被房主配置并全链路持久化 | 传参后 `snapshot().settings.board` 与 `roomInfo().board` 与入参一致；重启 `hydrate` 后同值；旧库缺列回默认 |
| M3 | 虚空语义正确 | 单测：贴着虚空的棋团，其「气」不含虚空格；虚空阻断的空区不合并计分；虚空格落子被拒 |
| M4 | 画布尺寸边界安全 | `1×1` 与 `100×100` 均可建、可开局、可结束，无越界崩溃；`0/101/负数/非整数` 被钳制回 `[1,100]` |
| M5 | 编辑器双入口可用 | 预设模板选择 + 手绘绘制/擦除/填充/矩形/形状↔虚空切换/尺寸切换/重置/保存/取消全部可用（§4） |
| M6 | rts 出生点 | 玩家**自选或随机**落于「可落子格」内，绝不出生到虚空 / 形状外 |

### 1.3 做与不做（Out of Scope，明确划线）

- **不改** go 的终局机（pass / 150 手 / 超时 / 认输 / wiped / last_standing）与数子口径（中国规则·子数+围空，F10）—— 只把「棋盘边界」从「矩形边界」推广为「形状边界 ∪ 虚空」（§6）；
- **不做**「虚空被包围后变色 / 转化 / 计分」（R4 已否）；
- **不做** rts 的「按形状连通块智能分配出生点」（R7 已否）—— 只做**自选 / 随机**；
- **不把** rts 的出生点概念引入 go（R7 已否）；
- **不做** 3D / 不规则多边形 / 非方格棋盘（仅方格拼成的正交形状）；
- **不做** 非房主改形状（仅房主，沿用 F8 的房主判定）；
- **不做** 棋盘形状的「中途改尺寸并迁移已有棋子」的复杂语义（中途改形状只对**尚未布局/新局**或**按边界重裁剪**生效，见 §9 Q3）。

## 3. 需求池

优先级：**P0 = 没它这个功能不成立**；P1 = 应该有的完整体验；P2 = 锦上添花。

### 3.1 形状数据结构（建议 · 供架构师采纳）

**表示方式：100×100 位图，每格三态。** 建议用两个 100×100 的位网格（或一个每格 2 bit 的网格）组合，逻辑上等价于每格取 `0 / 1 / 2`：

| 值 | 语义 | 可落子 | 计气/连通 | 计分 |
| --- | --- | --- | --- | --- |
| `0` shape-out | 形状外（棋盘之外） | ✗ | ✗（如同现状越界） | ✗ |
| `1` playable | 可落子（形状内） | ✓ | ✓ | ✓ |
| `2` void | 虚空格（形状内的「墙」） | ✗ | ✗（**阻断连通**，见 R4 / §6） | ✗ |

- **形状外（0）与虚空（2）在「不可落子 / 不计气 / 不参与计分」上等价**；二者**唯一区别**是：虚空是「形状内被划掉的一格」（UI 上属于形状内部，用于表达「墙」），形状外是「形状没圈到的格子」。**是否在 UI / 数据上区分二者见 §9 Q1**；**推荐数据上保留三态**（便于 UI 区分渲染与将来扩展）。
- **画布尺寸**：另有 `w × h`（`1 ≤ w,h ≤ 100`），位图实际有效区为 `[0,w) × [0,h)`；有效区外的位恒为 `0`。

**序列化格式建议（关键：需经 DB `TEXT` 列 + JSON 传输）**：

- 建议 `board.shape` 存为**紧凑字符串**：按行优先，每格一字符，`'.'` = 形状外、`'#'` = 可落子、`'x'` = 虚空；行间以 `'/'` 分隔。示例（3×3，中间挖空）：
  ```
  "###/#x#/###"
  ```
- 附带 `{ w, h }`（或与字符串冗余校验）。**不存 100×100 的 JSON 数组**（会膨胀 DB 与快照，100×100=10000 元素不划算）；紧凑串长度 = `w*h + (h-1)`，100×100 时约 1.01 万字符，可接受。
- **默认值（不配置时）**：`board = null` → 各模式回退到**现状矩形**（go 32×32 全可落子；rts 192×192 全可落子）。**即「不配置 = 行为零变化」**，与 F1/F2 完全一致（对照 `victoryLines` 不配时回默认的思路，F7）。
- **归一 `normBoard()`**（照抄 `normVictoryLines` 风格，F7/F9）：非法 / `null` / `''` / 解析失败 → 回 `null`（默认矩形）；`w/h` 用 `_clampInt(v, dflt, 1, 100)`；字符串长度与 `w*h` 不符 → 回默认；非法字符 → 视为形状外（或回默认，见 §7）。

## 5. 虚空格对 go 规则的影响（务必写清 · 只描述影响，不写实现）

> 现状：go 的边界 = 矩形边界（F11）。形状化后，**「边界」= 形状外 ∪ 虚空**（R4）。以下逐项说明影响，**实现细节留给架构师**。

| # | 规则点 | 现状 | 形状化后的影响 |
| --- | --- | --- | --- |
| G1 | **气与提子** | `_goLiberties` 用 4 邻数「空点」；越界 `continue` 不计气；同色向 4 邻扩展（F10/L131-152） | 虚空格的 4 邻**不算气**（与越界等价）；同色连通扩展时**虚空阻断**（不穿越虚空进入其后的格子）。贴着虚空的棋团，气只来自形状内的真空格 |
| G2 | **禁入点** | 越界 / 非空 → 拒绝（`oob` / `occupied`） | 虚空格与形状外**均不可落子**。**是否在 `reason` 上区分「虚空」与「形状外」**见 §9 Q2（建议：复用 `oob`，不新增 reason，保持前端兼容） |
| G3 | **自杀判定** | `_goPlayBatch` ④：未提子且整批落点所在团全无气 → `suicide` 回滚（F11/L302-310） | 计数用**形状化的 `_goLiberties`**（虚空不计气）。贴着虚空落子、形状内也无气且未提子 → 仍判自杀回滚；若形状内有气 → 合法 |
| G4 | **数子归属** | `_goEnclosedEmpty()`：洪水填充空区，接触单一阵营则归其；越界不计入 `borderF`（F10/L682-712）；`_goScoreChinese` = 子数 + 围空（F10） | **虚空 = 棋盘外**：洪水填充时**虚空格与形状外都视为不可穿越的边界**（不并入空区、不计归属）→ 虚空**阻断空区连通**（虚空前后两空区**分别**判归属，因此虚空可当「墙」围地，天然满足 R4）。虚空**本身不参与计分**（不产生归属、不计子数） |
| G5 | **`_goEnclosedEmpty()` 适配点** | 边界判定仅 `nx<0‖nx>=W`（矩形） | 需把「边界」判定扩展为 `越界 ∪ 形状外(board=0) ∪ 虚空(board=2)`；**三者在洪水填充中都 `continue`**（不并入空区、不加 `borderF`）。这是**唯一**需要改动的计分函数点 |
| G6 | **`_goScoreChinese()` 适配点** | 子数 = 逐格数 `_life != 0`；无棋盘概念 | 「子数」逻辑**天然无需改**（虚空 / 形状外本就永远为 `0`，不可能有子）；仅依赖 `_goEnclosedEmpty` 的空区归属改动 |
| G7 | **演化 `_goEvolveOnce`** | 8 邻计数，越界即死区（不计邻居）；诞生阈值 B3/S23 | 虚空格 / 形状外**不计入 8 邻邻居**（与越界等价）；虚空格恒为 `0`、永不诞生。**注意**：这会让「靠墙/靠虚空的活棋」邻居数变少、更易死——这是形状化玩法的**预期现象**（需在 QA 用例覆盖） |
| G8 | **劫 / KO** | `_goLoneLiberty` 找唯一气点 | 「唯一气点」的寻找同样需用形状化 `_goLiberties`（虚空不算气点） |
| G9 | **图案奖 / Voronoi 目数（旧口径）** | `_goPatternBonus` / `_goScore` 保留供 rts-go 快照（上一特性 A10 裁决） | 形状化后 `_goScore`（Voronoi）语义不变，但棋盘变小 → 数值变小。**`_goFinish` 用的是 `_goScoreChinese`，不受影响**；`_goScore` 仅供旧快照字段，**建议不改**（保持非回归） |

> **一句话总结**：go 侧只需把「边界」概念从「矩形越界」推广为「形状外 ∪ 虚空」，**改动集中在 `_goLiberties` / `_goEnclosedEmpty` 两处边界判定**；`_goScoreChinese` 的子数逻辑天然兼容。

## 6. rts 影响面（**风险区 · 待架构师深挖 · 本文不下技术结论**）

> rts 的整套玩法建立在「**192×192 全矩形世界**」假设上（F2）。形状化后，**这是本特性最大的未知风险**。以下**只列我担心受影响的功能点**，具体方案由架构师深挖。

| # | 担心受影响的功能点 | 现状锚点 | 我的担心 |
| --- | --- | --- | --- |
| R-A | **192×192 世界网格** | `WORLD_W/H=192`（F2） | 形状外格子如何表示（`terrain=VOID`？还是新标记）？世界生成 `_genTerrain/_genResources` 是否要在形状外停止填充？ |
| R-B | **32×32 生命棋盘层映射** | `LIFE_CELL=6`、`_lifeXY()`（F2） | 世界缩放到形状后，生命格如何映射？形状外是否冻结生命格？生命格与形状的对齐是否会错位？ |
| R-C | **8×8 区域控制** | `REGION_W=8`、`REGION_SIZE=24`、`_updateRegionControl()`（F3） | 形状变小后，很多区域会「完全没有可落子格」→ 区域数锐减 → 【领土】胜利线门槛（`TERRITORY_WIN=16`）可能**永远不可达**（见 §9 Q4） |
| R-D | **Voronoi 势力归属** | `_updateVoronoi()`、`INFLUENCE_R`（F4） | 形状外 / 虚空是否参与 Voronoi？是否应把它们排除出势力归属（否则「势力范围」会覆盖到棋盘外）？ |
| R-E | **护城河 / 城墙 / 包围捕捉** | `_captureEnclosed()`（F6）、A* 绕墙（`tests/algo_gameplay` #39） | 现有的「包围捕捉」以矩形边界为边界；形状外 / 虚空是否也被视为「不可穿越的墙」？（从 R4 语义看**应该**是） |
| R-F | **AI 寻路 / 出生 / 巡逻** | `ai.js` 用 `pickSpawn`、A*（F5/F6） | A* 是否要认形状外的格为障碍？AI 是否会寻路到棋盘外？AI 出生是否落形状内？ |
| R-G | **出生点** | `pickSpawn` 四角散布（F5） | R7 要求「自选 / 随机」，需保证候选点落可落子格内；玩家自选坐标的校验链 |
| R-H | **快照体积** | `lifeGrid` 32×32、`terrainSum` 等（F13） | 100×100 世界 + 100×100 生命层时，快照 / 网络传输是否过大？（生命层从 1024 → 10000 格，10×） |
| R-I | **资源生成 / 地形** | `_genResources`、`_seedOnboarding` | 形状外是否不生资源？onboarding 会不会把资源撒到棋盘外？ |

> **明确边界**：**我（PM）不对以上任何一条下技术结论**。本文只标注「这是一块需要架构师用实测/探针确认的风险区」，并给出**担心清单**，供架构师在架构文档中逐条裁决。

| 快照 | `snapshot().settings.victoryLines`（`engine.js` L1511） | `snapshot().settings.board` = `this.board`（或归一后的有效形状）；go 快照 `boardW` 与 rts `lifeW` 反映真实尺寸（F13） |
| 房间视图 | `roomInfo()` 输出 `victoryLines`/`availableLines`（`rooms.js` L264-267） | `roomInfo()` 输出 `board`（世界为权威，否则房间记录，否则默认） |
| 房主中途改 | `PATCH /rooms/:code/settings`（仅房主，F8） | 该路由 `patch` 增加 `board`（`normBoard` 后写 `room`+`World`+DB）；`setRoomSettings()` 增加 `board` 分支（`rooms.js` L323-337） |

> **确定性**：`normBoard` 为**纯函数**，不引入任何随机；预设模板的形状是**静态常量**；「随机岛屿」模板若需随机**必须走种子 rng**（`mulberry32`），**禁 `Math.random`**（IR-3a）。

## 11. 验收门槛（DoD）

1. P0 需求 **BE-01 ~ BE-18** 全部通过验收标准。
2. **不配置形状时行为零变化**：go 32×32 / rts 192×192 的落子、气、提子、数子、区域判定结果与改动前一致；`npm test` 320/320 全绿。
3. **画布尺寸边界**：`1×1` 与 `100×100` 均可建房、开局、落子、终局，无越界异常；越界输入被 `_clampInt` 夹回。
4. **go 虚空语义**：单测覆盖「贴虚空棋团的 4 邻不含虚空」「虚空阻断同色连通」「虚空阻断空区合并计分」「虚空格不可落子」。
5. **go 数子适配**：构造「虚空隔开两个空区」局面 → 两空区**分别**归属；虚空本身**不计子数、不产生归属**。
6. **rts 出生点**：随机 / 自选两种模式均可落于可落子格；非法坐标被拒/回退；**无连通块智能分配**。
7. **编辑器双入口**：预设模板 + 手绘编辑器（绘制/擦除/填充/矩形/形状↔虚空/尺寸/旋转/重置/保存/取消）全部可用。
8. **房主权限**：非房主改形状被拒（403 `not_host`）；房主改后下一次快照在其他客户端可见；重启后配置不丢。
9. 用「旧 schema DB + 旧内存房间」启动，无报错、读默认、可正常开局。
10. **确定性**：形状相关代码无 `Math.random` / `Date.now`（若沿用 go/ai 的 grep 守卫，需通过）。
