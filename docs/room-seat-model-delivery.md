## 二、最关键的一处玩法裁决（**请注意，这条改变了 go 的手感**）

**问题（我实测复现的）**：go 模式落子后，到**对手回合**的演化时，孤立棋子因 8 邻为 0 而死亡 —— 我在真实服务上实测 `lifeGrid[16][16]` 落子后变回了 `0`。

这**正是你之前在实时模式抱怨过的"落下的棋子会消失"**，而且和"以先后拓展位置来决定哪个抢占领地"直接矛盾：棋子站不住，就无所谓"先占先得"。

**裁决**：改成与实时模式**同一套设计语言** ——

> ~~**棋子不因孤独而死，只死于过度拥挤（n > 3）。**~~
> **⚠️ 本条已于 2026-09-10 被用户推翻，已作废。** 现行规则：标准康威 B3/S23，**孤子会死**（`n === 2 || n === 3` 存活）；补偿机制为每回合多颗落子（默认 3）+ 死亡宽限（默认 0）。详见 `docs/gameplay-rework-delivery.md`。

带来的三个结果：
1. **落子有持久意义**，单颗子也站得住；
2. **提子（围死）成为唯一的主动移除手段 —— 这反而更像围棋**；
3. 演化依然在棋子边缘持续诞生新细胞并向外扩张，"不可预测的数学"没丢。

如果你觉得还是该保留标准 B3/S23 的"孤子必死"，这是一行代码的事（`server/go.js` 的 `_goEvolveOnce`），你说一声我改回去。

### 线上实证的两个结论
1. **DB 回退路径在沙箱真实生效**：`/api/meta` 报 `node:sqlite`，说明沙箱内 `better-sqlite3` 未编译成功，自动回退到 `node:sqlite`——正是当初写回退的原因，生产环境已验证。
2. **反向代理劫持 `Authorization` 头的问题依然存在**，且多通道鉴权是唯一解法：
   - `GET /api/rooms?token=<jwt>` → `code 0` ✅
   - 不带 token → `401 invalid token` ✅
   - 仅带 `Authorization: Bearer <jwt>` → `401 invalid token` ❌（头被代理覆盖）
   - 客户端因此三通道并发（`?token=` / `x-auth-token` / `Authorization`），服务端**倒序**检查。
